# XR tool integration

Immersive viewing shares the asset scene, saved documents, and section plane with desktop. The first headset tool slice now exposes measurement through a PlayCanvas world-space menu and controller ray. Other tools still need immersive input and menu controls. All slices should reuse the existing `SelectionController`, `Measurement`, `Annotations`, `SavedPresets`, and segment workspaces; a separate XR document or mesh/splat editor would make edits diverge.

**Current UX gap:** The headset menu below is a functional prototype, not the accepted interface. The required design enters XR in Navigate and shows a head-following icon toolbar matching the desktop toolbar; only implemented tools are enabled. Choosing Measurement then opens a separate head-following options panel with the same saved list, name field, style controls, Save action, and collapse control as desktop. The current single text menu and automatic Measurement activation when the desktop tool was selected do not meet that requirement. Do not present this prototype as the finished XR measurement experience.

## Implemented measurement slice

The measurement options open when the web tool is selected. In AR/VR, a persistent camera-facing toolbar appears on entry whether the web tool was Navigate or Measurement. Selecting Measure arms point placement; it can also save or cancel a draft, cycle through saved measurements, and move either saved endpoint. A small white scene marker previews the surface point under the right-controller ray. A right-trigger tap places that point. Holding and moving the right trigger pans; the left trigger orbits, the left thumbstick zooms, and grips manipulate the artifact. Menu hits take precedence over right-hand surface picks and pan. Left-hand orbit remains independent of right-hand menu hover. Left **X** frames the artifact in front of the current head pose. Right **B** restores the initial VR framed pose or AR placement; another B within three seconds exits immersive mode. Menu tool choices synchronize back to the web panel after exiting XR, because a React panel transition inside PlayCanvas's XR input callback interrupts that update.

XR uses the same `Measurement` records, local coordinates, saved-item box, and scene renderer as the web view. The line is a world-space PlayCanvas cylinder in XR and the existing `WideLineRenderer` on desktop. A mesh surface tap uses a small PlayCanvas `Picker` target. CPU-sorted splats have no native Picker depth pixel in the installed engine version, so their taps query already-resident splat centers within the active segment, isolation, and section scope. The preview uses the same query while Measurement is armed, only after the controller or asset moves, and at most once per 120 ms. It stops when idle or a trigger drag begins. A splat point remains an estimated surface location. Desktop shows a small white cursor circle without rendering a new depth image on every pointer move; the actual point is resolved at click time.

Headset text entry and style sliders are not in this slice. XR Save uses the default `Measurement N` name; the web saved-item panel can rename it. The browser emulator verifies real menu clicks, two distinct points, stereo rendering, Save, moving an endpoint, navigation while measuring, document sharing, section coexistence, session teardown, and both mesh and splat formats. Quest 3 comfort, actual hit targets, text legibility, and frame time still need a device check before claiming headset usability.

## Input and menu boundary

The installed PlayCanvas `XrMenu` supplies controller-ray hover/click, hand poke, menu text, and action events. We attach it to the XR camera and pin it to the right of the view. It is a persistent palette, so its global `xr:menu:active` event must be cleared after opening; otherwise bundled `XrManipulation` blocks grips for the whole session. Actual right-hand menu hits still suppress surface picks and pan. The pinned script lacks a public show method, so the adapter calls its visibility method; review that boundary on PlayCanvas upgrades and verify placement, readability, and controller conflicts on Quest 3.

XR picks originate from `XrInputSource.getOrigin()` and `getDirection()` and convert hits through `ViewerSpace.toLocal` before storing them. Mesh picking reuses PlayCanvas `Picker` and model layers with one lazy 64×64 target; splat picking is described above. The surface preview reuses that target only while aiming, with no idle readback. XR UI hits take precedence. Further slices must test sections, segments, and model manipulation against their own pick semantics.

## Vertical slices

1. **Menu and measurement:** Implemented and browser-tested as described above. Quest device validation and headset naming/style input remain.
2. **Point annotations:** Reuse the same ray picker and annotation records. Provide marker placement, title and description entry through an XR-appropriate text input path, save/cancel, and stereo title/description display. Do not rely on DOM tooltips inside XR.
3. **Selection, paint, and segments:** Define a controller brush in object/world space with a visible preview and explicit visible-only/X-ray policy. Feed its result into the existing masks, histories, saved selections, color operation, and segment workspace. Saved region binding for annotations follows after region hover/pick works in stereo. Box/lasso need an XR-specific gesture definition; copying a 2D marquee into an eye view would be ambiguous.
4. **Views and sections:** Let controller handles rotate the asset relative to the fixed world axes, then save/recall through the existing view records. Expose cutting-plane normal, offset, tilts, flip, and Save through the same section state. Keep the plane and annotations in the shared scene and section picks on retained surfaces.
5. **Capture and remaining document actions:** Define a dedicated XR spectator capture rather than assuming the desktop canvas contains both eyes in a usable PNG. Expose saved-item open, rename, visibility, delete, undo/redo, isolation, and return-to-asset in the menu. Decide whether four-view remains a desktop layout rather than simulating four windows in a headset.

For each slice, run a real browser session with Meta IWER against development and minified production builds for both asset formats, plus a Quest 3 check for interaction comfort, text legibility, controller hit targets, stereo visuals, and performance. Compose each tool with sectioning, segment workspaces, existing saved records, XR manipulation, and session exit/re-entry. Benchmark render time and memory before adding a continuous controller preview or another pick pass. Emulator success does not establish headset usability.
