# Shared viewer tools and engine reuse

Mesh and splat viewers supply the same `SelectionController` contract to `SelectionControls`. Rectangle/lasso/brush gestures, modifiers, navigation, shortcuts, palette UI, selection/paint history, measurement state, and annotation editing are shared. `MeshSelection` and `SplatSelection` implement geometry-specific visibility, mask updates, and rendering. Tool components do not branch by asset type to implement operations; unit calibration remains a separate metadata concern.

`ViewerTree` consumes the same small named/visible item contract for selections, measurements, annotations, saved views, and saved sections. View/section snapshots share a small session preset collection; renaming a snapshot never activates it. Each tool has an explicit Save operation and a saved-items box above its options. Selection gestures/paint keep internal draft regions for rendering, overlapping paint, and annotation binding; only explicitly saved selections appear in the saved list and tree. Saving promotes the region with its packed mask and paint metadata; Update selection replaces that record without duplicating it. Clicking a saved selection restores its mask and leaves previous isolation, so Isolate can target that region. The model tree also opens and frames records through the same tool editors; its separate visibility and rename controls do not move the camera. Names synchronize into lists and open editors. Section eye controls apply the saved cut without restoring the camera or opening the editor. Reopening a section from its saved box restores its camera/orientation and offers Update section. Selection masks stay bit-packed; measurement and annotation models own their immutable edit histories. Eye controls affect only derived scene visuals, and renaming does not modify source assets or annotation note content.

## Paint example review

The official [paint example](https://github.com/playcanvas/engine/blob/main/examples/src/examples/gaussian-splatting/paint.example.mjs) uses `Picker` for surface positions, `GSplatProcessor` to paint a spherical brush into a `customColor` instance stream, and `setWorkBufferModifier` to combine that stream with the original color. It requests work-buffer updates after painting.

Our color operation applies an arbitrary sRGB shade to an existing selection mask. Immutable packed CPU colors provide immediate undo state; GPU work-buffer modification applies them to splats. A spherical brush processor would add a different operation and is unnecessary for this selection-based action. PlayCanvas does not supply the portal's color picker, selection state, or undo UI.

A spherical brush affects Gaussian centers within a 3D radius around a picked surface point. Our current brush selects inside a screen-space circle, with the chosen visible-only/X-ray policy. A sphere can also reach nearby surfaces inside its radius; it does not itself enforce front-surface visibility. It could support depth-local painting or future XR interaction, but is not required for select → color → annotate and is not a fix for tiny-triangle picking.

## Desktop and XR

Measurement state and visuals use one implementation for both asset formats and camera modes. White cylinder lines, sphere endpoints, and text are ordinary scene elements; projection and stereo rendering belong to the engine. The browser tool panels and annotation tooltip still require XR presentation and controller bindings when XR sessions are implemented. Those bindings should call the existing shared operations.

The runtime engine remains pinned in `package.json`. Embedded annotation layout has a small container adapter around the bundled manager; recheck it when upgrading the engine. Annotation markers use each visible viewport camera and the manager's native layers, without a dedicated annotation camera or render pass. Camera-facing visuals are replicated per visible panel; records and region masks stay shared. No editor framework or additional runtime dependency is imported.

`ViewerAnnotationManager` retains one engine mesh reference for its shared marker plane. Without that owner reference, replacing the last draft marker destroys the plane through `MeshInstance.destroy`, and the bundled manager reuses its destroyed vertex buffer for the saved marker. This causes repeated render exceptions that look like frozen navigation. The manager releases its reference on teardown; a regression test exercises the real mesh reference-counting behavior.

Selection binding snapshots the hovered area during pointer capture before the hover handler clears it, then commits on release without consuming the navigation events. Hover uses one outstanding GPU readback with no debounce delay. Mesh hover caches region index overlays sharing the original vertex data; entering a cached region switches instance visibility without rebuilding display geometry or invalidating the picker. Splat hover uploads its mask only when the hovered region changes. Cached previews are released on geometry edits and viewer teardown.

The pinned camera-controls input source does not clear held keyboard modifiers when the browser loses focus. `ViewerCamera` contains the narrow compatibility guard: it releases accumulated Shift/Ctrl state on blur and reconciles it with the next pointer event. Tool gestures consume their own captured pointer events, so they no longer disable and re-enable the complete camera script.

Measurement slider reset buttons restore the shared default line width and font size independently. Native endpoint gizmo size compensates for camera viewport height, keeping handles readable in four-panel layouts without additional geometry or render passes.

Focus is contextual: F frames the current mask in Selection, otherwise the entire asset (including after Q), with Measurement retaining its endpoint focus. Empty selections/measurements fall back to whole-asset bounds. The annotation form has no duplicate focus button. Stored selections remain available without affecting navigation focus.

## Segments

The Segment toolbar entry and Selection → Create segment use the same gestures, GPU area hover, saved-items presentation, and tool controllers as the asset workspace. Packed region masks scope the existing mesh subsets or native splat work-buffer modifier; geometry is shared. Each workspace owns its tool documents/history and saved section session. See [segments](segments.md) for behavior, cost, and browser verification. Seed growing and area/volume statistics are omitted.

## Selection coverage and shared option styling

Committed visible-only mesh gestures combine native PlayCanvas picking with an accelerated visibility supplement. `MeshPicker` crops the projection to the gesture's bounds and spends its 4 Mi-pixel budget there, rather than supersampling the entire viewport. A native crop already above the budget keeps its resolution, subject to the device texture limit. The synchronous projection/viewport overrides are restored before awaiting readback. IDs come from the native vertex index and PlayCanvas's `pickPS` encoder, without a CPU-generated color attribute or one MeshInstance per face. The offscreen RGBA8/depth target is single-sampled, reused, and approximately 32 MiB at 4 Mi-pixels, excluding readback. Hover remains at native resolution. Asset rotations participate in the pick-cache signature; geometry/index subsets update only when invalidated.

`MeshVisibilityQuery` uses the public `shapecast`, `raycastFirst`, and `raycast` APIs of pinned `three-mesh-bvh` 0.9.15, with Three 0.185.0 as its geometry/math peer. It follows the upstream centroid-visible selection approach while preserving GPU hits for partly visible faces and gesture boundaries. There is no Three renderer or scene. The worker tests only GPU-unhit candidates whose centers lie in the gesture; its rays start at the camera near plane, use the captured viewport/model transforms, and respect culling, section removal, isolation and segment scope. Indirect BVHs retain original face IDs. Rays target original triangle centroids and require the nearest retained hit to match the target part and face, without a permissive depth-tie tolerance. This is CPU BVH ray casting, not GPU ray tracing.

One worker is created lazily on the first committed mesh selection, with a single transferred copy of positions/indices and one BVH per mesh part. Segments and four-view panels reuse it; neither camera motion nor workspace changes rebuild the tree. Scope/visibility snapshots belong to the committed operation. GPU readback buffers are transferred to the worker, where both pixel decoding and visibility queries run off the UI thread. Existing generation/workspace checks reject stale results; errors reject pending requests, and viewer teardown terminates the worker. No BVH queries or picking passes run every frame or while idle. On the 1M non-indexed fixture, query geometry plus BVH occupies approximately 62 MB; total browser/GPU memory also depends on the decoder, model layout and driver. The worker bundle is approximately 167 KB minified / 48 KB gzip, loaded only when needed. Third-party MIT notices ship under `public/licenses/`.

The real 999,991-face scan regression originally missed 831 close-up-visible faces inside a brush stroke. `test:browser:visibility` checks the real gesture against a closer native GPU render, inspects isolated/focused output, records first-use and repeated-stroke timings, verifies idle query state and worker termination, and requires zero recorded misses. The separate `test:browser:coverage` fixture requires all 524,288 front-grid faces and zero hidden rear faces. The segment suite checks clipping, paint, annotations, measurements, history, cancellation and four-view composition on both formats. Run these in development and production as described in [browser verification](browser-verification.md).

These tests establish the covered regressions, not mathematically complete visibility for every possible mesh. A face with an occluded center and only an arbitrarily small visible sliver can still fall between GPU samples. There is no blanket “100% precision” claim or hidden-neighbour fill. The rejected polygon-subtraction prototype was too expensive on large fully occluded faces; it and its clipping/WASM dependencies are absent from the shipped implementation. The browser runs use Chromium/WebGL2; Safari energy use, WebGPU execution and actual immersive input/headset behavior remain unverified.

The existing scene uses continuous rendering (`autoRender=true`), independently of these edit-time queries. Idle selection work is zero, but that does not make the entire viewer idle or energy-free. Track native on-demand scene rendering, explicit tool invalidation and Safari profiling separately in the roadmap; do not add arbitrary pause timers that can hide asynchronous edits or interrupt camera damping/XR.

The Capture tool requests one completed engine frame and downloads the viewer canvas as a PNG. It adds no render loop, framebuffer, server upload, or persistent scene record. Four-view mode already renders all panels into that canvas, so the same operation captures the complete split layout. Browser controls, HTML tool panels, viewport labels, navigation widgets and DOM annotation tooltips are outside the scene canvas and are intentionally absent. Immersive-XR capture is a separate presentation concern and remains unverified.

Brush size is a percentage (1–50%) of the longest projected span of the active asset/segment bounds. Bounds are cached for the gesture owner and refreshed on asset orientation changes; pointer input projects only eight corners through the active native camera. Zoom and panel size therefore affect the brush consistently without scanning geometry every frame. All tool sliders use `SliderControl`; Save/Update and Clear/Reset/Cancel/Return use shared semantic green/red classes. The Return action sits beside the right-side options as a separate card.

Tree names open the corresponding saved editor and frame its region/endpoints/segment; point annotations center the marker at the existing camera distance. Views and sections recall their saved orientation/camera. Opening a hidden record reveals it. View draft cancellation completes before another tool applies its focus; rename and eye actions remain independent. Underlying operations still share native cameras and scene geometry. Browser panels and mouse brush input are not immersive UI/controller bindings; the outstanding WebXR work remains tracked rather than claimed as verified.
